状态：设计方案，尚未实现以下新增能力；不能作为生产验收证据。
基线：Phase156，提交 `37d023855ff748410769175d8449a1a6d27136e2`。

## 1. 修订目标与适用范围

对实际构建中发现的 RISC-V GNU 内联汇编，建立从原始发行源码、构建配置、宏定义及展开、类型与约束、翻译候选、目标产物到真实执行及独立审计的可追溯关系。所有已声明支持且满足前提的实例应完成工作链；尚缺证明或观察能力的实例保留明确阻塞，不能从实验分母移除。

首个目标语义域是编译器确认类型后的无符号整数乘法高半部，以及包含该 asm 的多语句宏。不是按宏名称、项目路径、行号或期待结果匹配。通用方法应支持同语义的改名、移位、不同宏嵌套和不同调用位置；其它语义域需各自证明，不能自动套用。

AST 中的出现记录不是动态执行次数、原生机器指令实例或独立程序数。跨构建配置、未捕获测试目标、任意 C、任意 ABI、任意浮点和完整内核执行均不能从本轮结果推导为已支持。

## 4. P0：冻结实例及实验分母

以 Phase156 账本为输入，新增不可变资格清单，而非覆盖历史发现文件。建立三个独立身份：源码定义身份、展开位置身份、上下文关联出现身份。每项保留发行来源、依赖文件内容摘要、上下文身份、检查编译器身份及原始位置记录。

去重必须基于实际关联，不依据计数除以构建变体数量。AST 路径仅是同一检查产物内定位手段，不是跨编译器稳定源码身份。相同函数名称不能合并不同 TU 的静态函数。位置缺失、相对文件名和虚拟文件应明确 unresolved，不猜主文件。

新增建议模块：`project_instance_eligibility.py`。输出语义族、直接/宏来源、待证义务和首个根本阻塞。该模块只描述资格；未执行验证时所有 approval 标志保持 false。

验收：所有发现记录恰好映射到一项资格记录，不能遗漏/重复；更换路径、重命名宏或调整源码位置不会改变支持原则。

## 5. P1：编译器宏来源与原生展开绑定

新增建议模块 `compiler_macro_provenance.py`；前端使用 Clang LibTooling 的预处理回调及 AST/SourceManager 连接，导出：

1. 宏定义文件内容身份、定义 token、参数、define/undef 生命周期和有效条件上下文。
2. 每次展开的立即/外层展开关系、调用 token 范围、实参 token、展开前后参数、相关声明身份与类型。
3. asm 模板、符号/数字操作数、约束、clobber、volatile/goto、读写关系及全部隐式效果。
4. token 拼接和字符串化的来源边；无法可靠恢复时保留明确缺口。
5. 字节偏移与行列号分开；所有偏移绑定文件内容，UTF-8 按字节计算。

对同一真实 native 构建命令采集 GCC 预处理证据，记录实际选中宏分支、语言、ISA/ABI、配置头和依赖。Clang 回调不能冒充 GCC 真实展开证据。可复用现有 native/inspection token 比较；其成功是接入前提，不是编译器全等价证明。

不得把 `<scratch space>` 当真实文件；它常来自 token 拼接。需通过展开链关联调用声明/符号。未知宏嵌套、内建宏或预处理差异应准确阻塞，不清洗差异 token。

验收：直接调用、嵌套宏、宏实参、宏重定义、条件分支、头文件多次展开均可重放；改变定义、实参、分支或依赖后，旧绑定必失败。

## 6. P2：通用 GNU 可交换输入合同

扩展 `GnuOperandContract`，保留原始约束，表示 modifier、约束替代项、读写/匹配关系及输入对。输入对关系必须在整条 asm 的操作数集合中校验，不能只在单个字符串解析器中推断。

- `%` 描述当前只读输入与其后一个输入的交换许可，不是模板中的操作数打印修饰符。
- 验证位置、后继输入、替代项一致性、重复/冲突修饰符及与 tied/early-clobber 的相互关系。
- 只有源语义在允许交换下对所有可见输出和效果成立，才允许后续候选消费该许可。
- 无符号乘法高半部可用交换律证明；非交换操作及带不等价副作用的表达式不能由操作名称猜测批准。
- 编译器输入表达式求值规则和寄存器分配交换是不同层次，不得因允许寄存器交换而重排 C 副作用。
- 将合同版本、允许排列及其证明身份加入 L2 权威、候选绑定、持久化和独立重放。

建议新增 `gnu_operand_relations.py`，原有限接口作为兼容包装；已支持的不含交换修饰符的约束行为不变。反例包括末尾输入标 `%`、输出标 `%`、不支持的替代项、多个冲突输入对、减法错误声明可交换。

验收：不再因合法、已证明的可交换输入而阻塞；非法或无法证明的情况仍拒绝。不可采用 `.replace('%','')`。

## 7. P3：指令、宏外壳与多输出的组合语义

复用已有 `RV64_MULHU_U64`，但逐段核验解码/提升、规范语义、候选选择、helper 注册、类型转换、ABI、链接及独立 L2 重放。仅注册 helper 不代表已打通这些消费链。

令实际编译器证明输入宽度为 w、无符号，中间乘积为 2w 位：低输出为乘积模 2^w，高输出为乘积右移 w。现有 helper 首期仅适用于 w=64；不由 typedef 名称猜宽度。

完整宏合同还必须描述：

- 临时变量的作用域、声明身份、输入初始化、转换和原语言规定的求值/先后关系。
- C 低位计算和 asm 高位计算的对象/值依赖，而不是只比较高位。
- 输出左值的类型、地址求值及写入顺序；同一对象、重叠对象、与输入别名的情况不能默认排除。
- 实参副作用、输出地址副作用、volatile/atomic 对象、限定符等的明确适用前提。
- helper 引入的调用、寄存器/栈/异常/全局效果与源合同的细化关系。

可先声明“无副作用地址表达式、普通整数对象”等有证明的子域，但不得把真实语料中域内的合法实例留成无解释阻塞。更广副作用需显式状态/序关系模型；不能重复求值参数或增加源未要求的 volatile/fence。

建议 `compiler_macro_effects.py` 导出通用 AST 语句/表达式关系，`l2_macro_authority.py` 消费其类型与效果证明。不得按宏名称、局部变量名或行号识别乘法。

验收：两个输出、原 C 外壳和允许输入排列一起闭合；故意交换输出、丢低位、错有符号性、破坏别名写入顺序均被发现。

## 8. P4：安全物化与防目标分支替代

首期优先采用**原生预处理产物上的受证明展开实例编辑**，保留完整 TU 和未修改周围代码。它是有来源的派生翻译产物，不是人为改动实验源数据库。必须连接：原始定义/调用 → native 展开 token → 检查 AST → 授权编辑区间 → 目标产物。

新增建议 `macro_materialization.py` 与版本化范围绑定；原 `fragment_source_range.py` 直接源码路线不放宽。每项编辑验证原 slice 内容、证明身份、边界、不重叠以及精确一次覆盖；同一宏调用包含多条 asm 时，不得用同一展开偏移覆盖整个调用。

备选的私有源码树/头文件定义级编辑，仅在证明该定义影响的全部用途及所有相关条件分支后启用；不能一项通过就批准全局修改。原发行树和源侧 GCC 构建继续使用原内容。

关键反旁路要求：x86 构建可能因架构宏改选项目已有实现。必须证明目标所编译的是经授权转换的原语义，而不是原项目的另一实现。不得给 x86 编译器简单注入 `__riscv` 或关闭 CPP 比较。

预处理 TU 仍可能含 ISA 属性、系统头定义及 ABI 特定布局。需要版本化、可证明的目标适配；不兼容时保守拒绝，不能删除属性、头文件或类型定义使其勉强通过。

验收：每个被选中的源实例具有唯一的目标处理状态；反例“只改代码但目标使用原 x86 分支”“修改一个头文件影响未批准调用”“遗漏宏内第二条 asm”均失败。

## 9. P5：版本化构建与预处理适配合同

扩展 `project_build_contract.py`、`project_compiler_compatibility.py` 和 `project_artifact_build.py`，分开表示：

- 原始 native 源 TU 与其真实构建；
- 原生预处理及检查输入；
- 授权翻译后的派生 TU；
- 目标适配、runtime 依赖、目标编译及链接。

新合同须绑定全部输入输出摘要、原参数及批准的参数差异、CPP token 映射、数据模型、目标文件架构、符号和依赖。保留原 exact-token 路线；经过证明的适配走新版本，不能用全局容错替换它。ABI/头文件不同不意味着可以无条件清洗 token。

逐项证明 target 必需的头文件、runtime、配置及 ABI 类型。不得直接拿源架构静态库或对象与目标链接。跨进程 FILE*、GMP 内部指针及对象内存映像也不可作为通用序列化格式。

验收：目标分支、目标架构、runtime 符号、依赖库或结构布局错误均在构建/合同阶段被识别；不是只确认编译器返回零。

## 10. P6：通用调用、对象与链接闭包

在既有受限 scalar 路线之外增加版本化 `compiler_typed_call_contract.py`，不要删除现有参数数量/类型检查后声称支持。

合同包含参数/结果类型、宽度/符号、ABI 分类、寄存器与栈位置、void/多输出、pointer→object 映射、大小/对齐/生命周期、边界、别名、可写区间及合法输入前提。需要类型驱动的编码与比较，而不是以函数名选择 harness。

对于 limb 数组，应由类型及调用/算法前提导出长度、有效区域及不变式；无证据时保留 `input-domain-contract-required`，不能凭参数名字生成“看起来能运行”的输入。观察返回值、输出对象、允许副作用以及异常/退出；不比较未初始化字节和无定义的 padding。

扩展 `compiler_call_inventory.closure()`，纳入必要头文件 callee、静态函数、跨 TU 调用、库初始化、分配器及全局效果。未知间接调用与递归仍需摘要/证明，不跳过。内部函数适配不能修改原函数语义或把简化副本计为原程序。

把 `build_driver()` 的隐含“第一个 driver、最后一个 body”规则扩展成有角色和依赖的单位图。每个 TU 保留自己的语言、宏和包含路径；禁止把同一 body 参数套给全部文件。库的 ISA/ABI、链接顺序、循环库依赖及运行时绑定均显式核验。

验收：多参数、多对象和多输出实例在真实源/目标构建中闭合；未知依赖被精确报告，不能在动态运行后才把缺少符号误记为翻译语义失败。

## 11. P7：分层验证与整体独立审计

| 层级 | 必须验证的内容 | 不足以作为通过的替代物 |
|---|---|---|
| L0 | 源/目标及依赖构建、ELF/ABI、runtime 链接、授权目标代码实际被消费 | syntax-only 或已有 x86 分支构建成功 |
| L1 | 源/目标局部操作、宽度/转换/输入输出映射，明确测试或证明范围 | helper 名称注册、固定几个期待值 |
| L2 | 宏来源、操作数交换、C 外壳效果、跨片段数据/对象依赖及输出闭包 | asm 单独等式、旧哈希重新签名 |
| L3 | 同一次真实调用的参数、对象、执行完成、可见结果与声明的事件义务 | 两个独立 toy wrapper、只观察高位 |
| 独立审计 | 从冻结原输入重建所有必需证据，核对实例/要求/目标产物精确覆盖 | 信任生产日志 verified 或聚合账本标签 |

把宏和整程序义务加入 requirement manifest、route selection、producer、consumer 和 `l3_production_acceptance`。每项要求都要有来源与消费身份；遗漏、重复、不相关证据及过时证据都拒绝。并非所有性质都适合动态事件观察：值等价、源约束、宏编辑授权分别使用其正确证据，不能把 token/指令计数相等当语义证明。

多次静态宏展开与动态执行次数分别统计；控制流可能使实例未执行或重复执行。动态覆盖不完整须如实报告，不能以静态出现数填充执行事件。物理微架构等价性不在本轮批准范围。

## 12. P8：实验账本与论文报告

分开报告定义位置、展开位置、上下文出现、含 asm 的 TU、程序入口、语义族和实际执行样本。共享一个语义族的重复展开体现工程覆盖，不等同于多个独立操作族创新。

冻结分层抽样规则后再运行翻译：按语义、宏/直接来源、参数/对象形状、调用闭包及 ABI 难度分层。成功/失败均保留，禁止事后只选择 helper 容易支持的入口。宏局部验证、函数级验证与整项目回归分别给出分母。

状态应区分发现、原生展开绑定、类型/约束绑定、编辑授权、翻译、构建、执行、审计。每个失败保留最早根因、后续未执行阶段和所有工件；上游失败时不能把下游记为通过或无 asm。

| C：可交换约束 | B 的操作数事实 | 有效排列被证明，非法声明拒绝，旧约束回归通过 |
| D：组合语义与 helper 接通 | B、C | 解码至目标完整合同，C 外壳和双输出同时验证 |
| E：安全物化与目标适配 | B、D | 目标实际消费授权变换，未批准分支不能旁路 |
| F：调用/对象/构建闭包 | D、E | 真实程序所有可达效应与必需输出有合同 |
| G：正式生产与独立审计 | A–F | 满足前提的全部义务闭合，失败与不支持保留在账本 |

允许在 C/D 交付后执行语义组件实验，但其通过不能代替 G。宏接入域和调用域的支持前提应先写入机器可检验合同；不承诺任意 C 程序的全状态等价。

## 14. 回归与反例矩阵

最低要求：

- 宏改名、参数改名、源位置移动、不同头文件路径和不同构建变体。
- 多次调用、嵌套宏、ifdef 切换、define/undef、拼接/字符串化及不可解析位置。
- 原始百分号约束、允许排列、非法最后输入、输出修饰冲突、非交换运算和 tied/early-clobber 组合。
- 无符号零/一/最大值/最高位/跨 limb 进位；固定种子的广泛值样本，不把有限样本称全输入证明。
- 独立宽乘法参考与已有 helper 交叉检验；若声称全域形式化性质，必须保存真实 bit-vector 证明、求解器与结果；超时/unknown 不能通过。
- 输入一次求值、输出同址/重叠、与输入别名、带副作用实参，以及不同合法求值关系。
- 低位丢失、高低互换、有符号乘法、错误移位、输出写序变化、错误调用约定及栈参数。
- 改成原生 x86 fallback、目标没消费补丁、未翻译第二个宏实例、头文件全局改动影响其它用法。
- 不匹配库/架构、缺 runtime、未知可达 callee、对象越界、padding/未初始化字节。
- 持久化 JSON 类型敏感比较、伪造完成标志、重新计算哈希后的篡改、依赖/工具/环境漂移。

既有 Phase155 类型稳定化、Phase156 全量盘点、直接非宏翻译、内存/原子/控制等已支持路线及冻结语料政策回归必须保留。

## 15. 当前信息是否足够、还需什么

现有源码及发现证据足够定位公共缺口、设计 A–G，不需要再次进行全量发现。但不足以仅凭源码片段批准全部真实程序执行。

实施 B/E/F 时需要按固定规则从已有工件提取：

1. 选定上下文的原始 GCC 命令、工作目录、生成配置头和依赖内容摘要，以及对应可验证对象。
2. 原生 GCC 预处理证据与检查器对应 token；相关类型事实及完整宏展开关系。
3. 按不同调用/对象形状预先选定的真实入口、可达对象/库依赖及合法输入要求。
4. 现有源/目标执行后端与观察合同的实际配置；未经确认不得假定所有后端可用于新对象/ABI。

这些是有针对性的证据补充，不要求重新下载、改动官方源码或反复运行全量构建。原生对象缺失/摘要不符时才重建对应捕获动作，并分别保存新证据，不能冒充旧产物。

## 16. 方案落地后的执行指导与停止规则

当前阶段：保存发现账本，不重新生成其完成状态；按资格清单冻结候选并完成宏/类型/构建合同。

实现 A–G 后依次运行：

1. 新合同正反例及持久化测试；真实 GCC/Clang 集成不得用模拟测试替代。
2. 既有直接源码与冻结语料回归；所有域外误拒绝和错误接受分别定位。
3. 固定真实宏实例的局部生产构建及独立重放；这里只能报告局部域。
4. 固定的真实函数/调用闭包生产实验，构建源 RISC-V 与目标 x86，运行其原生依赖和独立 harness。
5. 对每项要求进行 L0–L3 验证及从原工件发起的独立审计。
6. 通过后扩展全部声明域实例；公共根因首次失败就停止同类昂贵批次，保留剩余未运行项。
7. 在同输入、工具、配置、样本和义务下单独进行性能 A/B；不减少证明、样本或审计来获得加速。

具体端到端命令必须随实现后的真实 CLI 和已绑定执行合同提供。本方案分支没有新增这些执行入口，因此不能现在编造一条命令并声称已完成真实语料验收。
